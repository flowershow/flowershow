# Adversarial technical review: listing pages v4 (layout system)

Scope: `listing-design.md` v4 and `listing-implementation-plan.md`, checked against `origin/main` (temp worktree) and PR #1457 (PR A, open). Focus: views, knobs, `fields`, CSS contract, zero-config. Severity: BLOCKER = cannot ship as written; MAJOR = will visibly break or regress for real sites; MINOR = edge case, debt or doc drift.

No BLOCKERs found: everything is buildable as specified. Several MAJORs are bugs in the plan's own code that the planned tests will not catch.

## MAJOR

### M1. Grid and people are capped at 44rem, so the "3 columns at ≥1024px" spec cannot happen

- Where: B16 adds `.list-component[data-view] { max-width: var(--list-max-width, 44rem) }`, specificity (0,2,0). G2 adds `.list-component--grid, .list-component--people { max-width: var(--list-max-width, none) }`, specificity (0,1,0). The B16 rule wins regardless of source order.
- Failure: every `view: grid`/`people` listing is at most 44rem (704px) wide. With `--list-card-min: 17.5rem` and a 2rem gap, `auto-fill` fits 2 columns, never 3. People shows 4 columns in 704px (≈150px portraits). The `grid` `sizes` (`33vw`) then overstates image width.
- Why the tests miss it: B9/G1 tests check DOM only. Storybook screenshots would show it, but only if the reviewer counts columns.
- Fix: put the measure only on the views that use it: `.list-component--list, .list-component--compact { max-width: var(--list-max-width, 44rem) }`, and give `--grid`/`--people` no max-width. Add a Storybook play assertion: at a 1280px viewport, `getComputedStyle(grid).gridTemplateColumns.split(' ').length === 3`.

### M2. The new default rules out-rank every official theme's list typography and widths, contradicting "themes keep working"

- Where: B16 scopes rules as `.list-component[data-view] .list-component-item-headline` (0,3,0), `.list-component[data-view] .list-component-item-summary` (0,3,0) and `.list-component[data-view]` (0,2,0). The themes use (0,1,0)/(0,2,0): lessflowery, letterpress and superstack use `.list-component-item-content .list-component-item-headline`, and their `.list-component { max-width: var(--width-list-component) }` is 48rem / 64rem / 39rem. The `default-theme.css` header says themes win only "when their selectors are equally or more specific".
- Failure: any page that uses the new engine loses each theme's headline font size, margins, line-height, summary colour and list width. Letterpress's 64rem list shrinks to 44rem. Superstack's body-size headlines become 1.25rem. Legacy `<List />` is unaffected (no `data-view`), so a site "switching from `<List />` to the block" sees a different look. Design section 2 promises the opposite.
- Fix: wrap every new selector's scope in `:where()`, for example `:where(.list-component[data-view]) .list-component-item-headline` and `:where(.list-component--list) .list-component-item`. That keeps the defaults at (0,1,0) so theme rules win on source order. Only layout-critical rules the themes never set (the compact grid, the thumb `order`) may stay more specific. Add a Storybook story per official theme for the `list` view, not only `ThemedLetterpress`.

### M3. Leaf sites: the zero-config `/blog` renders as a broken 3-column grid of tiny thumbnail rows on deploy day

- Where: Leaf sets `.list-component { display: grid; grid-template-columns: 1fr 1fr 1fr }` at ≥768px (unlayered, so it wins over the default `display: flex`). The new `--list` rules (0,2,0)/(0,3,0) force `flex-direction: row` and a 160px thumbnail on each item, and `[data-view]` caps the root at 44rem.
- Failure: each card is about 14rem wide with a 160px thumbnail and a 1.25rem gap, leaving about 3rem for the title. This hits every Leaf site with a README-less or prose-only `blog/`/`posts/` folder as soon as PR B deploys (zero-config, no author action). The plan merges the C1 theme audit only "after B2 deploys", so the window is guaranteed. Compact rows inside Leaf's grid break the same way.
- Fix: make C1's Leaf change (scope Leaf's grid to `.list-component:not([data-view]), .list-component--grid`) a merge prerequisite of PR B, or have default CSS set `.list-component--list, .list-component--compact { display: flex !important }`. `!important` is the less good option, but it is the only way a layered default beats an unlayered theme. Applying the M2 fix also helps. Add a Leaf story.

### M4. `group: <field>` (and `group: year` with a non-date sort) produces interleaved, repeated headings

- Where: B4 sorts in `selectListingRows` by `spec.sort` only. B8 `renderListing` emits a heading whenever `item.group` changes ("each run").
- Failure: the design's own example, people with `group: team` and the default `sort: title`, renders `Design, Engineering, Design, Ops, Engineering…`, one heading per run. The same happens with `group: year` + `sort: title`, `group: status` on a projects grid sorted by title, and `group: month` + `sort: weight`. The G4 fixture plan ("grid grouped by status", "people by team") will show it, but nothing asserts it.
- Fix: when `group.by !== 'none'`, sort by group key first (date groups use the group's date direction; field groups use a locale-aware compare with "Other"/"Undated" last), then by `spec.sort` as a stable secondary. Add a unit test: people, `group: team`, `sort: title`, so each team heading appears exactly once.

### M5. Date slot and sort key diverge: `fields.date: pubDate` (Astro) or `published` gives a title-sorted feed with shuffled dates

- Where: B4 `sortValue(row, 'date')` always reads `itemDate(row)`, which is the `date` frontmatter key or the file-name prefix. `toListingItem` displays `fields.date` and `groupLabel` groups by it.
- Failure: an Astro migrant writes `fields: { date: pubDate }`. No post has `date`, so every row is "undated" and sorts by title, while the cards show pubDates out of order and `group: year` headings repeat (M4). This is the most likely customisation after `from`.
- Fix: define `sort: date` as "the date slot" (`fields.date` when it is set, else `date`), and use the same resolver for sort, display and group. Consider `pubDate`/`published` as built-in fallbacks for the `date` slot, and `author` as a fallback for `authors` (Jekyll/Hugo/Astro all use singular `author`; today it silently shows no byline).

### M6. "Server-rendered" is false for `layout: list` and zero-config Case 2 on `.mdx` pages, and for every page on `syntaxMode: mdx` sites

- Where: `components/public/mdx-client.tsx` is `dynamic(..., { ssr: false })`. Plan deviation 4 accepts this for `.mdx` and says the docs will cover it. It also applies to `.md` files on sites or pages with `syntaxMode: mdx`, and to any page where the `getConfig` query fails (`renderMode` becomes `undefined`, which selects the MDX path).
- Failure: for those pages the initial HTML has no items and no `rel=next/prev` links. Non-JS crawlers, link unfurlers and RSS discovery see an empty blog index. That is the exact #1120/#1008 audience (flowershow.app's own `blog/README.mdx`, once migrated). It also ships the whole listing a second time as compiled JS in the RSC payload.
- Fix: the implicit listing (`layout: list` and Case 2) is not inline content, so render it outside the MDX tree. In `page.tsx`, run `processMarkdown('', { listing: { implicit } })`, the same call `VirtualListingPage` already makes, and place the result after the compiled content. That makes the main listing server-rendered for every renderMode. Only inline blocks in MDX stay client-side; document that.

### M7. The cached folder result can exceed the 2MB Data Cache item limit, after which every request rescans the folder

- Where: B5 `queryListingRows` returns, inside `unstable_cache`, every listed row with its full `metadata` JSON (all frontmatter plus the computed description). The same applies to `from: ''` (whole site) and per `where`/`sort` variant.
- Failure: on Vercel, Data Cache entries over 2MB are not stored (Next logs "Failed to set Next.js data cache, items over 2MB can not be cached"). A 3–5k-post folder, or a smaller one with long frontmatter, silently becomes an uncached full-folder scan plus a JSON sort on every request, ×10 blocks. Nothing in unit tests (cache mocked) or CI e2e (tiny fixture) can reveal it. The design's "a few megabytes at most" is exactly the failure range.
- Fix: cache only the ordered `{id, path}` list (plus the group key) and fetch the current page slice's rows with `findMany({ where: { id: { in: sliceIds } } })`, about 20 rows per request. Or project the cached rows down to the fields the spec uses (title, date slot, sort key, `where` keys, `fields` keys). Add a unit test that the cached value contains no metadata keys outside those.

## MINOR

1. **Zero-config Case 2 detection disagrees with the plugin.** `hasExplicitListing` is a line-start regex (case-insensitive) while the plugin matches the AST `node.lang === 'list'|'blog'` (case-sensitive). A ```` ```blog ```` inside a callout or blockquote (`> ```blog`) or a list item indented 4+ spaces is not detected, so the README gets both listings. If that block has `pageSize`, it then shows "Only one list per page can paginate", because the implicit listing claims pagination first. ```` ```Blog ```` is detected as explicit but never rendered, so the page shows no listing at all. A `<List` in a code sample or prose suppresses it. Fix: decide Case 2 inside `remarkListing` ("append the implicit listing only if no targets were found") and pass `implicit: { auto: true }`.
2. **Virtual `/blog` (Case 1) fails for parent folders with spaces or non-ASCII names, and for a lowercase `readme.md`.** `decodedSlug` only maps `%20` to `+`, but `virtualListingDir` compares against raw blob paths (`My Blog/posts`, `Blögg/posts`). `filePathToSlug` treats only `README`/`index` (exact case) as index files, so `blog/readme.md` makes `virtualListingDir` return null while `/blog` has no blob, and the page 404s. Fix: compare `encodeSlug(filePathToSlug(dir))` against the slug, and use the same case rule as ingestion. `publicUrl: /${dir}` also needs `encodeSlug`.
3. **`UrlNormalizer` drops `?page`.** It does `router.replace(normalizedPath)` without the search string whenever the path contains `%20`, so page 2 of a listing under a spaced path snaps back to page 1. Fix: keep `location.search` (this also fixes the changelog).
4. **Avatar lookup rescans the whole site on every cache miss.** `cachedResolveAuthors` does `findMany({ where: { siteId }, select: { path } })` (every blob, images included) inside each per-handle-set cache entry, although the plugin already has `files`. Fix: cache `{id, path, appPath, permalink, title, avatarRaw}` and resolve avatar URLs outside the cache using `options.files`.
5. **Ten listings run sequentially.** `for … await build()` makes up to 30 awaited DB round trips on a cold cache, and two blocks with the same `from` and different `limit` fetch twice. Fix: build specs first, dedupe folder fetches with React `cache()`, then `Promise.all`, assigning pagination claims before the awaits.
6. **Times and timezones.** `resolveEntryDate` uses `toISOString().slice(0,10)`, so `date: 2026-12-31T22:00:00-05:00` lists as Jan 1 2027 and lands in the 2027 year group. Same-day posts sort by path, not by time. Fix: keep the author's calendar date for date-only/offset strings and sort on the full timestamp.
7. **Unquoted Obsidian wiki links.** `image: [[cover.png]]` and `authors: [[ada]]` unquoted parse as nested arrays (`[["cover.png"]]`), so `itemImage`/`normalizeAuthors` drop them silently. Fix: treat a single-element nested array as a wiki link.
8. **Dotted and nested keys.** `fields: { meta: [links.github] }` or `where: { meta.type: x }` silently match nothing (objects render nothing). Fix: error-card any key containing `.` until nested paths are supported.
9. **Image `src` is not sanitised.** `image: "#hero"`, `mailto:`, `data:` or a page target becomes `src="#hero"`, `"/blog/hero"` or similar. In dev, `next/image` throws on an unparsable `src`, and `.md` pages have no error boundary around `ListingImage`, so one bad post 500s the listing page in dev/CI. Fix: emit only `http(s)://` or leading-`/` asset URLs, otherwise no image; wrap `ListingImage` in the factory's `withErrorBoundary`.
10. **`--list-media-ratio` cannot be overridden from `:root`.** It is set on `.list-component[data-view]` itself, although the design says "set on `:root` or `.list-component`". Fix: read `var(--list-media-ratio, <per-ratio fallback>)` through an internal `--_ratio` variable.
11. **`is-disabled` lands in the "states" group with no `STATE_OWNERS` entry**, so the generated reference prints `| .is-disabled | State | undefined |`. Fix: add `'is-disabled': '.list-component-pagination-button'` in `scripts/theme-class-reference.mjs` and a test row.
12. **`featured` on `list` drops the measure.** `.list-component--list:has(.list-component-item--featured) { max-width: none }` widens the whole list, not just the hero, contradicting "list and its posts share one column". Fix: let only the hero break out, or keep the measure.
13. **Heading outline.** An inline block under `## Latest posts` with `group: year` emits `h2 2026` as a sibling of the section heading. A `layout: list` page goes h1 → h3. Fix: derive group/item heading levels from the preceding heading depth (the plugin has the AST), or use `h2`/`h3` only on `layout: list` pages.
14. **Pagination SEO edges.** Inline paginated blocks keep a bare canonical (acknowledged). Out-of-range `?page=N` returns 200 with a self-canonical, which creates an unbounded soft-404 space. Fix: set `robots: noindex` for out-of-range pages on `layout: list`, where the route can count cheaply from the cached ids (M7 fix).
15. **Stacked-PR mechanics.** B is branched from A and B2 from B, and the plan says "rebase onto `origin/main` once PR B merges". After a squash merge that replays B's commits and conflicts. Fix: `git rebase --onto origin/main feat/listing-pages feat/listing-views` (same for A→B), and retarget B2 before deleting B's branch.
16. **PR B docs advertise B2 features.** The B21 frontmatter description says "a grid, a team page" and the B21 `llms.txt` line says "blog index, grid…". If B deploys before B2, assistants following them write `view: grid` and get a public error card. Fix: keep grid/people wording out until G5. Also make the PR B "unknown view" error say "`grid` and `people` are coming soon; use `list`" rather than a generic error.
17. **Zero-config gaps elsewhere.** The virtual `/blog` is absent from the sitemap, search and the sidebar tree (folder stays a non-link), and `draft: true` posts stay in the sitemap. These are acceptable for v1 but unstated. Add them to the design's 4.10 "what changes" list.
18. **Avatar size mismatch.** The renderer passes `sizes="20px"`, `ListingImage` hard-codes `width={24}` and ignores `sizes`, and CSS forces 20px. This is harmless but three sources of truth; pick one.
19. **Local verification gaps.** The route branches (B15 canonical, B27 Case 1/2 precedence versus tags, changelog and real pages), `unstable_cache` behaviour, and theme interplay are verified only by CI e2e. Fix: extract a pure `resolveListingRoute({ slug, blob, siteFilePaths, metadata, content })` and a pure canonical helper, and unit-test the precedence table locally. Add Storybook stories that load each official theme's CSS (the themes repo is local), so M2/M3 are visible without Docker.

## Checked and fine

- hName nodes plus `ListingImage` as `mdxJsxFlowElement`: `remarkMdxJsxToElement` runs after the listing plugin in the md chain. `rehypeResolveHtmlUrls` leaves the leading-`/` hrefs and `http(s)` srcs the renderer emits alone, and MDX's explicit-JSX resolver ignores them, so URLs agree across pipelines. The parity test through `serialize`+`hydrate` is the right gate.
- The placeholder-id approach correctly keeps listing headings out of the `rehype-slug` counter. Autolink only processes headings with an `id`, and the strip runs before it.
- The whole-card `::after` overlay is not clipped by the headline's `overflow: hidden`: its containing block is the article, an ancestor of the headline.
- Cache invalidation on author or person page edits: every publish's finalizer posts `revalidateTag(siteId)` (`apps/cloudflare-worker/src/publish-finalizer-workflow.js`). Listing rows and author entries share that tag, with a 60s fallback.
- `?page` survives middleware rewrites, and the route is dynamic, so there is no ISR key issue.
- Blob paths are stored rootDir-stripped by sync, so `from` without a rootDir prefix is right. Stripping a leading rootDir name only matters for a site whose root folder name is also a real subfolder (rare).
